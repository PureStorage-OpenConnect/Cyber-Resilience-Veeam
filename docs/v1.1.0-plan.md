# Everpure NAS backup-from-snapshot scripts for Veeam: plan for 1.1.0

Status: in development on `feature/v1.1.0`, based on 1.0.0 (released 2026-10-22). The 1.0.0
plan, [unified-nas-snapshot-plan.md](unified-nas-snapshot-plan.md), still describes the
architecture; this document only covers what 1.1.0 adds.

## 1. Scope and priorities

| Prio | Feature | Outcome |
| --- | --- | --- |
| 1 | Auto-discovery | A job configuration names the job, nothing else. Shares come from the job at run time, each share is mapped to its array through the array's file interfaces, arrays live in one global file, and the last known state is cached. |
| 2 | ActiveCluster for File | Shares in a synchronously mirrored FlashArray realm work whichever array of the pair is active, including after a failover between pre and post. |
| 3 | File-to-tape jobs | A Veeam file-to-tape job with SMB/NFS shares gets the same treatment as a file backup job: job guard, discovery, snapshots. |

1.0.0 configuration files keep working unchanged (semantic versioning, MINOR release). Where
1.1.0 behaves differently with a 1.0.0 file, section 6 says so and the changelog lists it.

## 2. Auto-discovery (prio 1)

### 2.1 The global arrays file

`arrays.jsonc` lists every array the scripts may use, once for all jobs:

```jsonc
{
	"Arrays": [
		{ "Name": "fa01", "Endpoint": "fa01.example.com", "ApiTokenFile": "secrets/fa01.token" },
		{ "Name": "fb01", "Endpoint": "fb01.example.com", "ApiTokenFile": "secrets/fb01.token" }
	]
}
```

* A job configuration finds it through `ArraysFile`, default `arrays.jsonc` in the job
  configuration's directory (the generator puts both into `jobs/`). Relative token paths resolve
  against the arrays file's own directory.
* `Arrays` inside a job configuration (1.0.0 style) still works. Both sources are merged; a name
  defined in both is a configuration error, not a silent override.
* Per-array keys stay as in 1.0.0 (`Platform`, `Tls`). No array needs to say which shares it
  serves.

### 2.2 Shares from the job

With `Veeam.JobId` set and a backend that lists job objects (PowerShell), the job is the share
list. Each object's share root (`BackupObject[].Server.Path`, or for tape `Object[].Server.Name`)
becomes one share, deduplicated. Objects that are not SMB or NFS shares (an S3 bucket, a Windows
server path) are reported and skipped.

`Shares` becomes optional. An entry is now an **override** for one share of the job, matched by
path: `Array` pins the array, `Source` pins the managed directory or file system. An override for
a path that is not in the job is a warning and is ignored.

Without `Veeam.JobId`, or with the REST backend (which does not list job objects), `Shares` is
required as in 1.0.0 and is the share list.

### 2.3 Mapping shares to arrays

For every share without an `Array` override:

1. Take the host part of the path (`\\host\share`, `host:/export`). An IP literal is used as is,
   a name is resolved with DNS (all A and AAAA records).
2. Read the file interfaces of the arrays (`GET network-interfaces`): on FlashArray the enabled
   interfaces whose `services` include `file`, address in `eth.address`; on FlashBlade the
   enabled interfaces whose `services` include `data`, address in `address`, plus `server.name`.
   **Assumption to confirm in the lab (V1).**
3. The share belongs to the array that owns one of its addresses. No owner: the share is
   unmapped. Two owners: a configuration error, unless they form an ActiveCluster pair
   (section 3).
4. The FlashBlade server name of the matching interface narrows the export lookup. That resolves
   an export name that exists on two servers, which 1.0.0 had to refuse. FlashArray does the same
   with the export's `server` once V1 shows where the realm server appears.

Which arrays are contacted:

* First the arrays the cache (2.4) recorded for these shares. If every share maps to one of
  them, nothing else is contacted.
* Otherwise every array in the arrays file. An array that cannot be reached or rejects its token
  is a **warning** as long as every share still maps somewhere, and an **error** when a share
  stays unmapped (it might live on exactly that array).

### 2.4 State cache

One JSON file per job configuration: `<state directory>/<profile>.state.json`. The default
directory is `<install>\state` on Windows and
`/var/lib/veeam/scripts/sandbox/everpure-veeam-nas/state` on the appliance (the only persistent
writable place for job scripts there). `State.Directory` overrides it. The pre phase writes it
at the end of a successful run, the post phase after cleanup; a dry run never writes it. It holds
no secrets:

```jsonc
{
	"Version": 1, "Profile": "files", "JobId": "…", "JobName": "files", "Written": "2026-10-23T08:15:00Z",
	"Shares":  [ { "VeeamPath": "\\\\192.0.2.10\\finance", "Protocol": "SMB", "InventoryId": "…", "Array": "fa01", "Source": "fs01:finance" } ],
	"Sources": [ { "Array": "fa01", "Platform": "FlashArray", "Source": "fs01:finance" } ]
}
```

What the cache is for:

| Situation | Without cache | With cache |
| --- | --- | --- |
| Normal run | every array contacted for mapping | only the arrays that served the shares last time |
| A share was removed from the job | its source's tagged snapshots stay forever | post and sweep keep cleaning the cached source until no tagged snapshot is left there, then drop it |
| Post: an array is unreachable | its sources are skipped | they stay in the cache and the next run cleans them up |
| Post with `-NoJobGuard`, Veeam unreachable, no `Shares` list | nothing to clean up | the shares of the last run are cleaned up |
| ActiveCluster failover between runs | — | records which array of the pair served each source (diagnostics) |

**Not** a use: applying the fail-safe to cached shares when the job cannot be read. With the
job guard on, reading the job and proving that this job started the script are the same call. If
it fails, the caller might be a clone, and the phase must change nothing. With the guard on, the
share list is always known once the guard has passed. The 2026-10-22 idea of caching the share
list "for the sentinel" therefore does not apply. The post phase's disarm already covers a pre
phase that cannot reach Veeam.

The cache never overrides what the job and the arrays say in the current run. A state file of
another job (different `JobId`), a missing one or an unreadable one is ignored with a warning,
never a failure.

### 2.5 Generator and sample

* `New-EverpureVeeamJobScripts.ps1` writes `jobs/arrays.jsonc` from `arrays.sample.jsonc` if
  it does not exist yet, and a job configuration without `Arrays` and `Shares` (just
  `Veeam.JobId` and commented examples of overrides).
* The job lookup by name also finds file-to-tape jobs.
* "Next steps" says what is actually left: add the arrays once, store their tokens, verify.
* `Protect-EverpureVeeamSecret.ps1 -Array <name> -Endpoint <address>` adds an array to
  `arrays.jsonc` (inserted as text, so the file's comments survive), then stores and verifies its
  token at `secrets/<name>.token`. `-Array <name>` alone reads path and endpoint from the file, so
  the endpoint is only ever typed once.

### 2.6 Verify

Prints the share list as discovered from the job, the mapping of each share (array, matching
interface address, source), every array it could not reach, the cache file and its age. A share
that stays unmapped is a problem; an override for a share outside the job is a warning.

## 3. ActiveCluster for File (prio 2)

A realm in a stretched pod is served by one array of the pair at a time, either one. Lab setup:
two FlashArrays with SMB and NFS shares in such a realm. Nothing is designed before V3 to V9
answer how the arrays present it. Working hypothesis:

* Both arrays go into the arrays file; nothing marks them as a pair, the scripts detect it.
* The realm's file VIP is listed on both arrays, enabled (or active) only on the serving one.
  Mapping takes the serving array; if both report it, the pair is recognised by the pod and either
  can be used.
* Directory snapshots of a stretched pod exist on both arrays, so pre, post and the sweep may use
  whichever array is reachable, and a failover between pre and post does not invalidate the
  snapshot path.

Open questions, each a lab test in section 5: how the VIP looks on the passive array; the full
managed directory name in a stretched pod; whether snapshots can be created and destroyed on
either array; whether `keep_for` is honoured on both; whether the share sees the snapshot under
`.snapshot` right after creation; what happens to a job reading from the snapshot during a
failover.

## 3a. Fleets (to explore)

Everpure Fusion groups arrays into a fleet. A REST 2.x call made after logging in on one member
runs on another when it carries `context_names=<member>`; returned items name the member in
their `context` field. A mutating call takes exactly one context, a GET may take several and
answers 207 with per-member errors. The lab has a fleet.

Possible design, not built: an arrays-file entry for a fleet (one endpoint, one token); the
members are listed and their file interfaces read with `context_names`, then shares map as in
2.3, and every array call carries the member's context.

Risk to design around: Fusion engineers note that endpoints which do not support
`context_names` silently ignore it, so a snapshot create or destroy could run on the login
array instead of the member. Every fleet call must therefore check that each returned item
names the expected `context` and fail closed otherwise, like the FlashBlade `source.name`
re-check. Questions V11 to V14 in section 5.

## 4. File-to-tape jobs (prio 3)

Verified on 13.1.1.18 (2026-10-22/23): a file-to-tape job honours the share's storage snapshot
mode and the fail-safe path, and runs pre/post scripts like a file backup job.

| | File backup job | File-to-tape job |
| --- | --- | --- |
| Lookup | `Get-VBRUnstructuredBackupJob -Id` | `Get-VBRTapeJob` (no `-Id`), filter by `Id`, type `FileToTape` |
| Share roots | `BackupObject[].Server.Path` | `Object[].Server.Name` where `Server.Type` is `CifsShare` or `NfsShare` (`Object[].Path` carries an `nfs41://` prefix for NFS) |
| Inventory ID | `BackupObject[].Server.Id` | `Object[].Server.Id` (same ID as the inventory share) |
| Active sessions | `Get-VBRUnstructuredBackupSession -Name` | `Get-VBRTapeBackupSession -Job` (`Get-VBRSession -Job` warns that it does not support tape jobs) |

The job lookup becomes one function that tries both kinds and returns the same record. The REST
backend stays file-backup-only.

## 6. Compatibility with 1.0.0 configurations

| 1.0.0 file | 1.1.0 behaviour |
| --- | --- |
| `Arrays` and `Shares`, no `Veeam.JobId` | unchanged |
| `Arrays`, `Shares` and `Veeam.JobId` (PowerShell backend) | the job is now the share list. A job share missing from `Shares`, which 1.0.0 backed up live (verify reported it), is now protected. A `Shares` entry that is not in the job is no longer repointed, only warned about. `Array` and `Source` of the entries still apply. |
| REST backend | unchanged (`Shares` required) |

The generator creates `jobs/arrays.jsonc` with an **empty** list (examples commented out), so a
1.0.0 job folder with its own `Arrays` does not suddenly gain sample arrays with missing tokens.
